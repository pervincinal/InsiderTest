# Playtest

## Headless balance run
```bash
cd tower-clash && npm run playtest           # all levels
npm run playtest -- --level 12 --seed 3      # one level
npm run playtest -- --seeds 100              # robustness sweep: gate 100 % wins for levels 1–8, ≥ 95 % after
# seeds reproduce the browser exactly: window.__towerclash.loadLevel(id, seed)
```
Prints a table: level, result for reference player (win/lose + time), result for idle player (must not be win), enemy-vs-enemy stalemate flag. Exit code 1 if any level fails a gate. Paste the table into the daily report when levels changed.

## Daily Challenge, Weekly Challenge and twist gates (CI)
```bash
npm run playtest -- --daily 2026-09-18 --days 30 --seeds 3   # each day's challenge (level 9–50, fixed seed, twist), K seeds from the fixed one
npm run playtest -- --daily 2026-09-18 --days 30 --no-twist  # control: same days without the twist (blame the level, not the twist)
npm run playtest -- --weekly 2026-09-21 --weeks 26 --seeds 5 # each week's challenge (Monday key; level 33–50, fixed seed, non-plain twist, 3★ target = star3)
npm run playtest -- --weekly 2026-09-21 --weeks 26 --no-twist # control for the weekly, as for the daily
npm run playtest -- --twist lean --seeds 5                   # every pool level under one twist: plain | lean | fastFeet | thinWalls | reinforced
npm run playtest -- --twist lean --seeds 50 --pool 36-36     # --pool a-b (inclusive, default POOL_FROM–POOL_TO = 9–50): one level, a band, or 1–50
```
Gates (exit 1 on failure): daily — every day's fixed seed won and wins/K ≥ 90 %; weekly — every week's fixed seed won and wins/K ≥ 80 % (the 3★ target is informational: the row's "best / target" and "3* by" columns show the fastest seed and which seed reached `star3` — `fixed`, `seed N` or `NONE`; star3 sits at 0.9 × the bot's median by design, so most weeks show `NONE`); twist — every pool level wins ≥ 80 % of its seeds (4/5 at K = 5, GDD §7.5 item 3). `--weekly` takes only a Monday (UTC) key and errors on anything else; the current week's Monday in bash is `date -u -d "-$(( $(date -u +%u) - 1 )) days" +%F` (GNU `'monday this week'` gives the *next* Monday on Tue–Sun). `--weekly`, `--daily` and `--twist` are separate modes; `--pool` only applies to `--twist`.

Reading a weekly failure: (1) `4/5 < 90%` or a lost fixed seed → run the same weeks with `--no-twist`: passes without the twist → a level fix under that twist (GDD §3), fails both → plain level bug; then `--twist <id> --seeds 50 --pool <lvl>-<lvl>` — under 45/50 is a balance bug, one lost seed near the fixed one is not. (2) `no seed <= 3* target` → check the plain campaign row (`npm run playtest -- --seeds 5`, column 3*/2*/1*/0*): 0/5 3★ there too means the `star3` clock is out of the reference player's reach on that level regardless of twist — a clock item for the Level Designer (or a bot-speed item for the AI Engineer), not a twist item.

`.github/workflows/tower-clash-ci.yml` runs all three after the headless playtest: "Daily challenge gate" (`--daily $(date -u +%F) --days 90 --seeds 3`, ≈ 10 s since QA-11 2026-09-28), "Weekly challenge gate (26 weeks x 5 seeds)" (`--weekly <this week's Monday> --weeks 26 --seeds 5`, blocking — the 3★ target is not gated, so there is no `continue-on-error`; 9.8 s locally on 2026-10-19, K = 3 6.0 s) and "Twist pool gate" (all five twists at `--seeds 5`, ≈ 2.6 s each). Use K = 5 for the weekly and the twist gate, in CI and in the daily QA sweep alike: at K = 3 the 80 % rule demands 3/3, which is stricter than the spec and fails on a single robust-but-not-perfect week or level (QA-29: `--weekly 2026-10-19 --weeks 26 --seeds 3` prints `FAIL 2027-03-29 lvl 50 The Crown Reforged [lean]: 2/3 < 80%` for the one lost seed 139975; K = 5 reads 4/5 ok). The daily gate stays at K = 3 (below K = 10 its 90 % rule means every seed won at any K, so K = 5 would only cost time). When a twist row fails, rerun it at `--seeds 50` before touching the level — a level under 80 % at K = 50 is a balance bug for the Level Designer (file it under "Bugs" in `docs/BACKLOG.md`); a single lost seed at K = 5 is not.

## Naive human line (QA-3) and the CI naive gate
```bash
npm run playtest -- --naive --seeds 5                 # first-time human model on every level, react 4000 ms (informational)
npm run playtest -- --naive --seeds 5 --react 8000    # slower hands
npm run playtest -- --naive --seeds 5 --gate 1-16     # asc gate: exit 1 when a level of 1–8 wins < 4/5 or a level of 9–16 wins < 3/5
npm run playtest -- --naive --seeds 5 --gate 1-16 --tie both --tie-exempt 3   # the CI step (QA-30): both tie orders, level 3's tie desc row exempt (GD-7h)
npm run playtest -- --naive --level 12 --seeds 5 --gate 12-12   # one gated level (a-b must contain --level)
```
`scripts/lib/naivePlayer.ts`: every `--react` ms (first action at 3 s) each own tower with a free link streams to its nearest non-own tower (neutral before enemy); it never unlinks, never boosts, and re-links a tower that lost its streams only after another reaction delay. One row per level (wins/K, stars, median, `holds` = ≥ 50 % wins, `star2?` = holds and median ≤ star2, `gate` = ok / FAIL / `-` outside the gated range) and the summary line `naive: N/50 levels won at >= 50 %, M within star2`. Without `--gate` the mode is informational (exit 0): levels 1–8 are expected to hold — a `NO` there is a level/design item for the Level Designer / Game Designer, traced with the losing seed before filing.

`--gate a-b` (`naiveGate` / `NAIVE_GATE_BANDS` in `scripts/lib/naivePlayer.ts`, unit-tested in `tests/ai/naive.test.ts`): every level id in a..b must win ≥ 80 % of its seeds for levels 1–8 (4/5 at K = 5) and ≥ 60 % for 9–16 (3/5); the range may not go past 16 (later levels have no threshold and stay informational), the thresholds are defined at the default 4000 ms reaction (`--gate` with `--react` is refused), and a level of the range that was not run counts as failed (a partial `--level` run cannot pass). Failed rows print `FAIL lvl N name: w/K < 80% (need 4/5, lost s1,s2)`; exit 1 when any. CI runs it as "Naive human gate (levels 1-16 x 5 seeds)" right after the twist gates (≈ 13 s: all 50 levels are simulated, the gate reads rows 1–16). Reading a failure: rerun `--naive --level N --seeds 5 --gate N-N` to confirm, then replay the losing seed in the browser (`window.__towerclash.loadLevel(N, seed)` without autoplay, tapping what the bot would: every 4 s each own tower streams to its nearest non-own tower); a level under its share is a level/design item for the Level Designer (file it under "Bugs" in `docs/BACKLOG.md` with the losing seed), not a bot item — the bot is fixed by design.

Literal card follower (GD-6h, GDD §3.12 item 12 (a)): `npm run playtest -- --naive --level N --follow "prio=a,b,c;hold=home;noprioFrom=x" --seeds 20 [--react MS]` runs the naive line, except that each free link goes first to the first tower of `prio` (in order) that the source has a lane to and does not own (else the plain naive target), `hold` towers open no link before L2 (unless they already streamed once), and `noprioFrom` towers ignore `prio`; `--prefer a,b [--hold c]` is the same spec in two flags (do not mix with `--follow`). Tower ids are the level's (an unknown id is an error), so it needs `--level N`; it refuses `--gate` and `--daily` / `--weekly`, and exits 0. It prints the naive row (wins/K, 3*/2*/1*/0*, median, losers) and a `rule (a)` line — the card rewrite passes when the follower wins at least the level's naive gate share at 4 s and its median is within `star2` (`-> ok` / `-> NO`). Reproduces the GD-6 table: 7 `prio=fwd` 5/20, 6 `prio=outpost --react 8000` 0/20, 10 `prio=fort` 16/20. The spec lives in the GD item, not in the level JSON. Code: `followTarget` / `parseFollowSpec` in `scripts/lib/naivePlayer.ts`, tests in `tests/scripts/follow.test.ts`.

Own-count gate and reversed tie (GD-7f, GDD §3.12 (i) (c), §3.13 (f)). `--follow` also takes `after=id:k[,id:k]` — the `prio` tower `id` is a target only once the player owns ≥ k towers at the reaction (the card's "with five towers take the guns"); before that the source tries the next `prio` tower, then the plain naive target (which may still be that tower: `after` gates the card, not the naive line); every `after` id must be in `prio`. Reproduces GD-7c/d/e (20 seeds, 4 s, 2026-10-20): 13 `prio=guns,outpost;after=guns:3,outpost:4` 20/20 71.9 s, 14 `prio=east,mid,guns;after=guns:5` 20/20 70.4 s, 16 `prio=east,camp,guns,keep;after=camp:5,guns:5,keep:7` 20/20 61.4 s. `--tie asc|desc|both` (campaign `--naive` only, combines with `--follow`, `--react`, `--level`): on an exact tie of the naive target key (neutral-first, lane length) `asc` (default) takes the smaller id — today's gated line, output byte-identical to before GD-7f — and `desc` the larger, i.e. the other side of every mirror pair (`e…`/`east`/`ne`/`se` sort first, so `asc` always starts east). `desc` prints only the reversed line; `both` prints one extra row per level labelled `tie desc` under the level's own row, one summary line per order (`naive:` / `naive tie desc:`). Reference rows (`--naive --seeds 20 --tie both`, d4810f6 levels): `tie desc` 3 0/20, 5 1/20, 7 20/20 89.9 s 0 × 2★, 11 67.2 s, 13 80.1 s, 14 70.2 s, 16 70.0 s, the rest of 1–16 within 4 s of `asc`. `--gate a-b --tie both` gates both orders — a level fails when **either** is under its share (`FAIL lvl 3 Free Real Estate [tie desc]: 0/5 < 80% …`, summary `N failed level(s) (asc A, tie desc D)`, ≈ 21 s for 1–50 vs ≈ 13 s); `--gate --tie desc` is refused (it would drop the gated line). Since QA-30 (2026-10-21, after LV-22 fixed level 5's west start by layout) the CI step "Naive human gate" gates both orders: `npm run playtest -- --naive --seeds 5 --gate 1-16 --tie both --tie-exempt 3` (0 failed on the tree with LV-22; ≈ 20–25 s locally vs 16.6 s for `asc` only). `--tie-exempt a[,b]` (only with `--gate … --tie both`, ids inside the gate range) takes those levels' `tie desc` row out of the gate — the row prints `exempt` in the gate column and an `exempt lvl N … [tie desc]: w/K — <reason>; not gated` line, the summary reads `(asc A, tie desc D, tie desc exempt N)`; their `asc` row stays gated. Only levels in `NAIVE_TIE_EXEMPT` (`scripts/lib/naivePlayer.ts`, id → item id + reason) are accepted: today 3 — GD-7h cured its west first tap with the tutorial steer (step 1 completes only on home → east), which the naive model never reads, so its `desc` row is 0/5 by construction. **A future level cured by a tutorial (not a layout) goes into `NAIVE_TIE_EXEMPT` with its item id and onto the step's `--tie-exempt` list in the same change** (`tests/repo/hygiene.test.ts` QA-30 pins the step text and that its list equals the registry). When an exempt row recovers the runner prints `now passes: drop it from --tie-exempt` — then drop it from both. `reclock.ts`'s `star2` floor stays on the `asc` median. Tests: `tests/scripts/naiveTie.test.ts`, `after=` in `tests/scripts/follow.test.ts`.

Challenge naive rows (QA-7): `npm run playtest -- --daily <day> --days N --naive` and `--weekly <monday> --weeks N --naive` run the naive first-time line instead of the reference player (K seeds, 4 s reactions, twist applied) — informational, exit 0, one row per day/week; `--gate` and `--twist` do not combine with it.

## Browser smoke (Playwright, Chromium preinstalled)
```bash
cd tower-clash && npm run build && npm run e2e
```
Covers: title renders → level select shows locked/unlocked → level 1 loads → reference player drives to win via `window.__towerclash.autoplay()` → result screen with stars → screenshots in `e2e/__screenshots__/`. Do not run `playwright install`; use `PLAYWRIGHT_BROWSERS_PATH=/opt/pw-browsers` (already set).

Parallel runs (QA-4): `playwright.config.ts` reads two environment variables so agents sharing the checkout never need a scratch config. `PW_PORT` (default 4173) sets both `baseURL` and the preview server's `--port --strictPort`, so two agents on different ports get their own `vite preview`; `PW_OUTPUT` (default `test-results`) sets `outputDir` (traces, failure screenshots), so one run's cleanup does not delete another's artefacts. Example: `PW_PORT=4192 PW_OUTPUT=<scratchpad>/pw-qa npx playwright test --project=chromium e2e/smoke.spec.ts` (after `npm run build`). Only the Producer runs the plain `npm run e2e` on the default port. Since QA-28 (2026-10-18) the config also takes `PW_DIST=<dir>` (serve a scratch build instead of `dist/`, e.g. `npx vite build --outDir <scratchpad>/x-dist --emptyOutDir`) and holds a run lock per output directory: a second live run on the same `PW_OUTPUT` fails fast naming the variable (stale locks from dead pids are taken over).

CI shards (QA-26): `tower-clash-ci.yml` runs the chromium project as the matrix job `e2e (shard N/2)` (`npx playwright test --project=chromium --shard=N/2`, own runner, `PW_PORT` 4191 / 4192, `PW_OUTPUT=test-results/shard-N`, each shard builds dist/ itself, in parallel with the check job; the WebView and PWA projects stay in the check job). `--shard` hands whole files to shards by test count in path order, which is why the 53-test level content suite lives in `e2e/integrity/content.spec.ts` (sorts after `gestures430.spec.ts`: ≈ 50 / 50 of the time); `tests/repo/hygiene.test.ts` (QA-26) pins the split — when it fails after new tests, re-measure per-file times and rebalance (only past a 20 % gap between the shards; QA-30, 2026-10-21, 169 tests: 105 / 64 tests, 372 / 375 s locally, CI 297 / 338 s — kept). Local dry run of one shard: `PW_PORT=4191 PW_OUTPUT=<scratchpad>/pw-shard1 npx playwright test --project=chromium --shard=1/2` (after `npm run build`).

PWA offline (QA-8): `npm run e2e:pwa` runs `e2e/pwa.spec.ts` in the `pwa` project — the only project with the service worker allowed (BUG-16 blocks it everywhere else): first launch registers public/sw.js and precaches the shell, second launch puts the entry chunk + idle preloads (level 1, lazy screens) in the runtime cache, `context.setOffline(true)` → the title and level 1 boot from the cache, a cold level chunk fails with the `common.loadFailed` toast, back online it loads on the next tap. The project has `retries: 1` (the BUG-16 stall, ~1/500 boots on the worker path; every step is still bounded, the test 60 s) and writes to `<PW_OUTPUT>/pwa`. `setOffline` reaches worker-routed requests only because the config sets `PW_EXPERIMENTAL_SERVICE_WORKER_NETWORK_EVENTS=1`; without it the worker's fetch handler still hits the server. Parallel: same `PW_PORT` / `PW_OUTPUT` variables, `--project=pwa`. Since 4f2ddf6 (BUG-18 fixed) the first launch alone must cache the entry chunk. QA-9 (2026-09-27) added two more tests in the same project: **upgrade** (the previous worker is route-served with `CACHE_VERSION` n−1, then `registration.update()` installs the real one — old cache deleted on activate, new cache holds the shell, the shell boots offline right after) and **new deploy** (every chunk re-hashed through routes; network-first navigation picks up the new index, the offline launch after that boots the new shell). Known gap (BUG-19): the upgrade drops the runtime cache (level chunks), so the spec warms it with one online launch before playing level 1 offline until public/sw.js carries `./assets/*` over on activate.

## Manual feel check (for the report)
Run `npm run dev`, play levels 1–3 with mouse; note anything that reads badly at 360 px width. Log findings under "Bugs" in `docs/BACKLOG.md`.
