## 0b. How to publish on the App Store — the Apple account is verified (written 2026-09-28, PUB-12, for a stakeholder with an iPhone and no Mac)

Everything happens in a browser (developer.apple.com, appstoreconnect.apple.com, github.com) and on the iPhone. Signing certificates and provisioning profiles are created **by the CI runner** (Xcode cloud signing with an App Store Connect API key) — no Mac, no Xcode, no `.p12`. The workflow is `tower-clash-ios-release.yml` (Mobile Engineer, in progress on 2026-09-28: archive, sign, upload to TestFlight; secrets `APPLE_TEAM_ID`, `APP_STORE_CONNECT_API_KEY_ID`, `APP_STORE_CONNECT_API_ISSUER_ID`, `APP_STORE_CONNECT_API_KEY_P8`). Field texts to paste are in **`APP_STORE_CONNECT_SHEET.md`** (the "sheet"). Steps 1–5 are **one-time**; step 6 repeats **per build**; steps 7–8 repeat **per version**.

**Default for 1.0.0: submit without in-app purchases (sheet variant B).** The build is made without `RC_IOS_KEY`, so the shop hides its Crystals and Bundles tabs (PUB-14, 2026-10-03) and shows only Skins and Upgrades — no price, product or Restore Purchases button is reachable; skins and Commander upgrades keep working with crystals / gold earned in play (the converter and the booster crate sit on the hidden tabs and come back with 1.0.1). No products, no Paid Applications agreement, no RevenueCat for this version — the review notes say so (sheet §6.4 B). The build sent to App Review is **1.0.0 (8)**, the first with the real AdMob ids (§0c step 9). IAP + RevenueCat follow in **1.0.1 (build 9)** once MZ13 is done (sheet variant A, A18).

**Prerequisites still open before step 7 "Add for Review" (not before TestFlight):**
1. ~~GitHub Pages~~ — **done 2026-09-28** (W3): `https://pervincinal.github.io/InsiderTest/privacy.html` and `…/support.html` are live since the Pages deploy of that day; **confirm once in Safari** (the team's sandbox cannot reach github.io).
2. **Support e-mail placeholder** — `[developer e-mail]` (4 places in `tower-clash/public/privacy.html`, 2 in `support.html`) and `[developer name / address]` must be replaced before review: send the two values in the report thread (§0 step 3, G18 / T3); the next push republishes the pages.
3. **iPhone-only target** — done 2026-09-28 (Producer): `TARGETED_DEVICE_FAMILY = 1` in both build configurations of `ios/App/App.xcodeproj`, so App Store Connect asks for iPhone screenshots only (an iPad set would otherwise have been mandatory; `STORE_LISTING.md` §2 recommends iPhone-only).
4. **Real AdMob iOS ids** (`ADMOB_IOS_APP_ID`, `ADMOB_IOS_INTERSTITIAL`, `ADMOB_IOS_REWARDED`, MZ7 — free, ≈ 30 min, needs only a Google account; the AdMob app is linked to the store listing later) — without them the build shows Google's "Test Ad" placeholders, which is fine on TestFlight and not fine on the public App Store.
5. **No `RATING_PROMPT` variable when build 8 is made** (added 2026-10-08, PUB-16) — GitHub → *Settings* → *Secrets and variables* → *Actions* → *Variables*: `RATING_PROMPT` absent or not `on` (the default; nothing to do). The review notes (sheet §6.4 B) tell Apple that this version never asks for a rating; the variable is for 1.0.1 at the earliest (§5, MM-10). TestFlight check TF-21 looks at the same page.

1. **Team ID (one-time).** https://developer.apple.com/account → *Membership details* → copy the 10-character **Team ID** (e.g. `AB12CD34EF`). Keep it for step 4.
2. **Register the bundle id (one-time).** developer.apple.com/account → *Certificates, Identifiers & Profiles* → *Identifiers* → "+" → **App IDs** → Continue → type **App** → Continue → *Description* `Tower Clash`; *Bundle ID* **Explicit** `com.pervincinal.towerclash`; *Capabilities*: leave the defaults, make sure **In-App Purchase** is ticked (it is on by default; harmless in 1.0.0, needed in 1.0.1) → Continue → **Register**. Nothing else (no Game Center, no Push).
3. **App Store Connect API key (one-time).** https://appstoreconnect.apple.com → *Users and Access* → *Integrations* tab → *App Store Connect API* → **Team Keys** → "+" (Generate API Key) → *Name* `GitHub CI`; *Access* **Admin** (needed once so the CI can create the distribution certificate and profile; can be downgraded to *App Manager* after the first successful upload) → **Generate**. On the page note the **Issuer ID** (top, a UUID) and the new row's **Key ID** (10 characters), then **Download API Key** → `AuthKey_<KEYID>.p8`. **The file can be downloaded only once** — if lost, revoke the key and make a new one. Do not send the file anywhere except step 4.
4. **Four GitHub secrets (one-time).** https://github.com/pervincinal/InsiderTest → *Settings* → *Secrets and variables* → *Actions* → **New repository secret**, four times, names exactly: `APPLE_TEAM_ID` = the Team ID of step 1; `APP_STORE_CONNECT_API_KEY_ID` = the Key ID; `APP_STORE_CONNECT_API_ISSUER_ID` = the Issuer ID; `APP_STORE_CONNECT_API_KEY_P8` = the **whole text** of the `.p8` file opened in a text editor, including the `-----BEGIN PRIVATE KEY-----` and `-----END PRIVATE KEY-----` lines (on the iPhone: open the file in Files → share → copy; on a PC: Notepad). Then write "iOS secrets added" in the report thread — the team never sees the values, only whether the workflow passes.
5. **Create the app record (one-time).** App Store Connect → *My Apps* → "+" → **New App**: *Platforms* iOS; *Name* `Tower Clash` (if "taken": `Tower Clash: Tap & Conquer`, then `Tower Clash Strategy` — sheet §1); *Primary Language* English (U.S.); *Bundle ID* the one from step 2; *SKU* `towerclash`; *User Access* Full Access → **Create**. The name can be changed later; the bundle id cannot.
6. **Build → TestFlight (per build).** GitHub shows the *Run workflow* button only for workflows that exist on the default branch `main`, and the repository's workflows live on `claude/tower-war-game-plan-weqwpb` — so **write "run the iOS release" in the report thread and the team triggers the run through the GitHub API** (works on any branch), or create the release tag (§0 step 1: `tower-clash-v1.0.0` on the build head — a tag push starts the iOS *appstore* lane and the Android lane; the same upload shows up in TestFlight). A third way, once a run exists: *Actions* → the latest **tower-clash-ios-release** run → *Re-run all jobs* (works from Safari on any branch). Wait ≈ 20–30 min (macOS runner: build, sign, upload) plus ≈ 15–30 min of Apple "processing". Then App Store Connect → *My Apps* → Tower Clash → **TestFlight** tab → build **1.0.0 (7)** appears under iOS builds. If a *Missing Compliance* badge shows, click *Manage* → encryption **No** (sheet §6.6). Install on the iPhone: TestFlight tab → *Internal Testing* → "+" → group `Team` → add your own user (sheet §7) → the invitation e-mail arrives → install the free **TestFlight** app from the App Store on the iPhone → accept → Install. Play levels 1–3 and one Daily Challenge; write what you saw in the report thread (T7 / MM-1 for iOS). Every later build (1.0.0 with the real AdMob ids = build 8, 1.0.1 = build 9, …) repeats only this step.
7. **Version page → Add for Review (per version).** App Store Connect → Tower Clash → *App Store* tab → **1.0.0 Prepare for Submission**, in this order, all from the sheet: (a) screenshots — `tower-clash/store/screenshots/apple-6.7/en/01.png … 10.png` into the iPhone 6.9"/6.7" slot in file order, `apple-6.5/en/01 … 10` into the 6.5" slot only if that tab is shown (sheet §6.1; a 13" iPad slot means prerequisite 3 is not done yet); (b) *Promotional Text*, *Description* (variant B block), *Keywords*, *Support URL*, *Marketing URL*, *Copyright* (sheet §6.2 / §6.3); (c) *Build* → "+" → **1.0.0 (8)** (the build with the real AdMob ids, §0c step 9; build 7 has Google test ads and stays on TestFlight); (d) *App Review Information*: Sign-in required **No**, contact name / phone / e-mail (yours), *Notes* = variant B (sheet §6.4); (e) *Version Release* **Manually release this version**; **Save**. Then the left menu: (f) *App Information* → Subtitle, Category Games › Strategy / Casual, Content Rights No, **Age Rating** questionnaire (sheet §5, expect 9+), Privacy Policy URL; (g) **App Privacy** → Get Started → the data types and answers of sheet §4 (variant B: no *Purchase History*), Tracking **No** → **Publish**; (h) **Pricing and Availability** → Free; countries **Azerbaijan, Türkiye, Kazakhstan, Georgia** (default of `POST_LAUNCH.md` §2.2; all countries at week 4). Back on the version page → **Add for Review** → **Submit to App Review**. Review usually takes 1–3 days; Apple writes to the contact e-mail; a rejection is answered by the team in the report thread (the text is written for you, you paste it in Resolution Center).
8. **Release (per version).** When the status is **Pending Developer Release** → *Release This Version*. Nothing happens automatically before that click. The next version (1.0.1 / build 9: IAP, RevenueCat) repeats steps 6–8 only, with sheet variant A.

## 0c. AdMob account and ad ids — "AdMob hesabı və reklam ID-ləri" (written 2026-10-02, PUB-13, for a stakeholder with an iPhone and a browser)

Without these ids every store build shows **Google's test ads** ("Test Ad" label, no revenue): when the secrets are empty, `tower-clash-ios-release.yml` keeps Google's test app id in `Info.plist` and the build uses Google's test units (`ADMOB_TEST_UNITS` in `src/economy/providers/config.ts`); on the `appstore` lane the job only prints a warning. That is fine on TestFlight and **not** fine on the public App Store (§0b prerequisite 4). Everything happens in a browser (admob.google.com, github.com; a computer is easier, Safari on the iPhone also works). Free, ≈ 30 min. Steps 1–8 and 11 are **one-time**; step 9 repeats only when an id changes; step 10 is the rule for TestFlight with real ads. This section closes **MZ7** (iOS half: steps 1–5; Android half: step 6) and **MZ8** (step 7). **MZ12** stays open until the W7 decision (step 8).

What the code needs, and nothing more: **one Interstitial unit** (placement `int_level_break`, the only interstitial in `AD_PLACEMENTS`, `src/economy/catalog.ts`) and **one Rewarded unit** shared by the four rewarded placements `rv_double_gold`, `rv_continue`, `rv_free_booster`, `rv_daily_chest` (`rewardedByPlacement` in `capacitor.config.ts` is empty, so all four use the single `rewarded` id). No banner, app-open or native units.

1. **Sign in (one-time).** https://admob.google.com → *Get started* → sign in with a Google account (the one for the future Play Console is fine) → country, time zone, payment currency (USD) → accept the AdMob terms → *Create AdMob account*. Payment details and the address PIN come later (`ACCOUNTS.md` §5.4 step 7) and are not needed for the ids. The account may show "getting ready" / "under review" for a few days; ids can be created meanwhile.
2. **Add the iOS app (one-time).** Left menu *Apps* → **Add app** → platform **iOS** → "Is the app listed on a supported app store?" **No** (it is not live yet) → *App name* `Tower Clash` → **Add app**. The confirmation page shows the **App ID** `ca-app-pub-<16 digits>~<10 digits>` — with a **tilde `~`**. Copy it (it stays under *Apps* → Tower Clash (iOS) → *App settings*).
3. **Two ad units (one-time).** On that page *Create ad unit* (or *Apps* → Tower Clash (iOS) → *Ad units* → **Add ad unit**): (a) **Interstitial** → *Ad unit name* `tower_clash_ios_interstitial` → advanced settings untouched → **Create ad unit** → copy the **ad unit ID** `ca-app-pub-<16 digits>/<10 digits>` — with a **slash `/`** → *Done*. (b) **Add ad unit** → **Rewarded** → name `tower_clash_ios_rewarded` → reward amount `1`, reward item `Reward` (the game decides the reward itself and ignores this value — `admob.ts` only listens for the "rewarded" event); server-side verification off → **Create ad unit** → copy the ID → *Done*.
4. **Content settings (one-time).** The code already sends *max ad content rating G* and *not child-directed* on every start (`maxAdContentRating: General`, `tagForChildDirectedTreatment: false` in `src/economy/providers/admob.ts`); set the same in the console so it matches MZ7: *Blocking controls* → *All apps* → *Content* → **Maximum ad content rating: G** → Save. If AdMob asks whether the app is directed at children: **No**.
5. **Three GitHub secrets (one-time).** https://github.com/pervincinal/InsiderTest → *Settings* → *Secrets and variables* → *Actions* → **New repository secret**, three times, names exactly: `ADMOB_IOS_APP_ID` = the App ID of step 2 (`~`); `ADMOB_IOS_INTERSTITIAL` = the ID of step 3a (`/`); `ADMOB_IOS_REWARDED` = the ID of step 3b (`/`). No spaces, no quotes. An ad unit id in `ADMOB_IOS_APP_ID` would crash the app at start, so the release job stops with an error when that value has no `~` (the run fails instead of shipping); an App ID in one of the two ad-unit secrets is not checked — it does not crash, but no ad ever loads, so make sure both contain a `/`. Then write "AdMob iOS secrets added" in the report thread.
6. **Android (later, same clicks).** When the Play app record exists (G2): *Apps* → **Add app** → **Android** → not listed → `Tower Clash` → App ID → secret `ADMOB_ANDROID_APP_ID`; ad units `tower_clash_android_interstitial` → `ADMOB_ANDROID_INTERSTITIAL` and `tower_clash_android_rewarded` → `ADMOB_ANDROID_REWARDED`; then add the Android app to both messages of step 7. The Android release job (G5) reads them; nothing changes for iOS.
7. **Privacy & messaging (one-time, MZ8).** Left menu *Privacy & messaging*: (a) **European regulations** (GDPR: EEA, UK, Switzerland) → *Create message* → *Apps*: Tower Clash (iOS) → *Privacy policy URL* `https://pervincinal.github.io/InsiderTest/privacy.html` → language English (add others if offered) → user choices: keep **Consent** and **Manage options**, add **Do not consent** if offered → ad partners: Google's default list → **Publish**. (b) **US state regulations** → *Create message* → same app, same privacy URL → **Publish**. (c) **Do not** create the **IDFA explainer** (iOS tracking) message: the game never shows Apple's tracking prompt (MZ9 option A), so that message would never appear and would contradict App Privacy "Tracking: No". What the game does with them (`src/economy/providers/admob.ts`): at start `requestConsentInfo()`; where Google says consent is required (EEA/UK/CH) and the form exists, `showConsentForm()` once, before any ad loads; **Settings → Privacy options** appears only when UMP reports the options as `REQUIRED` and reopens the form with `showPrivacyOptionsForm()` — for players in the regulated US states this is where the US-state message opens. iOS always asks for non-personalised ads whatever the answer. Without a published message the form never shows, the Settings entry stays hidden and ads still run non-personalised (the code tolerates it), so this does not block TestFlight — publish before the public release.
8. **app-ads.txt (MZ12 — not blocking App Review).** AdMob → *Settings* → *Account information* → **Publisher ID** `pub-<16 digits>`. The team's file `docs/publishing/app-ads.txt.example` needs that id and must be served at the **root** of the developer website (`https://<domain>/app-ads.txt`); `https://pervincinal.github.io/InsiderTest/` is a sub-path and is never crawled, so it waits for the **W7** decision (a user-site repository `pervincinal.github.io`, or a custom domain). Write the choice and the publisher id in the report thread; the team prepares the file. Ads serve without it (some buyers skip the app, lower fill); Apple does not check it.
9. **Rebuild with the real ids (per id change).** write "run the iOS release" in the report thread (the team triggers it through the GitHub API — the *Run workflow* button needs the workflow on `main`, see §0b step 6), or *Re-run all jobs* on the latest run. The log shows `VITE_ADMOB_IOS_INTERSTITIAL: set`, `VITE_ADMOB_IOS_REWARDED: set` and the `plutil` step writing `GADApplicationIdentifier`. Install as in §0b step 6.
   - **Build numbers (policy, Producer 2026-10-03):** build **7** is the current release candidate — no AdMob ids, so Google test ads; TestFlight only. The first build with the real AdMob ids is **build 8**, still version **1.0.0**: when the three secrets exist, write "AdMob ids added, rebuild" in the report thread — the Producer raises `config.buildNumber` to 8 and runs `npm run version:sync`, then the run is started; **1.0.0 (8)** is the build submitted to App Review (§0b step 7c). **1.0.1 with in-app purchases is build 9** (§0d step 7). Apple accepts each build number only once per version, so build 7 is never re-uploaded with the real ids.
10. **TestFlight with real ads.** From that build on the iPhone shows **real ads** (no "Test Ad" label) once AdMob serves the account — new accounts and apps not yet linked to a store often get few or no ads for the first days; then the interstitial simply does not appear and the rewarded buttons stay hidden (the game hides them when no ad is loaded) — that is not a bug. **Never tap your own ads** and do not replay rewarded videos to "test" — AdMob treats that as invalid traffic and can suspend the account. If AdMob asks to register a test device (*Settings* → *Test devices* → *Add test device* → iOS), it wants the device's advertising ID, which this game never reads (no tracking prompt); if you cannot obtain it, skip the registration and just do not tap ads — the ad flow itself was verified with Google's test ads.
11. **After the App Store release (one-time).** AdMob → *Apps* → Tower Clash (iOS) → *App settings* → *App store details* → **Add** → search "Tower Clash" → select → Save. AdMob then reviews the app ("app readiness"); full serving starts after that. Same for Android after the Play release.

## 0d. RevenueCat and in-app purchases (1.0.1) — "RevenueCat və satınalmalar (1.0.1)" (written 2026-10-02, PUB-13, for a stakeholder with an iPhone and a browser)

1.0.0 ships without purchases (§0b, sheet variant B). This section turns them on for **1.0.1 (build 9)**: nine products in App Store Connect, a RevenueCat project that validates the receipts, one GitHub secret `RC_IOS_KEY`, a sandbox test, then the build with sheet variant A. All in a browser (appstoreconnect.apple.com, app.revenuecat.com, github.com) plus the iPhone for the test; ≈ 1.5 h of clicks plus Apple's 1–3 days for the agreement. The order matters: agreement → products → key → RevenueCat → secret → build. Steps 1–6 are **one-time**; steps 7–9 are **per version**. This section closes **MZ2**, **MZ3**, **MZ4** (upload), and the iOS halves of **MZ13** and **MZ14**; the Android halves (MZ1, MZ5, MZ6, the Play app in RevenueCat, `RC_ANDROID_KEY`) wait for G1–G2.

Before you start: §0b steps 1–5 done (the app record exists, A9) and you are the **Account Holder** (only that role can accept the agreement).

1. **Paid Applications agreement (one-time, MZ2).** App Store Connect → **Business** (old name *Agreements, Tax, and Banking*) → *Paid Apps* → **View and Agree to Terms** → accept; **Bank Accounts** → add (IBAN, SWIFT, holder name as on the Apple account); **Tax Forms** → W-8BEN (individual, not a US person) or W-8BEN-E (company) — details in `ACCOUNTS.md` §5.2. Wait until the agreement says **Active** (usually 1–3 days). Until then the products of step 2 stay "Missing Metadata". Optional, free, halves Apple's commission: the Small Business Program (`ACCOUNTS.md` §5.2 step 8).
2. **Nine products (one-time, MZ3 + MZ4).** App Store Connect → *Apps* → Tower Clash → left menu **Monetization → In-App Purchases** → "+" → *Type*, *Reference Name*, *Product ID* from the table below (**Product ID exactly** — it can never be changed or reused) → **Create**. On each product page: *Availability* → all countries or regions → Save; *Price Schedule* → **Add Pricing** → base country **United States (USD)** → the price from the table → Next → Next (Apple fills the other countries) → Confirm; *App Store Localization* → "+" → **English (U.S.)** → *Display Name* and *Description* from the table → Add; *Review Information* → *Screenshot* → `tower-clash/store/iap-review/shop-crystals.png` (one file for all nine; on the iPhone: GitHub → the file → Download → Save to Files) → Save; *Family Sharing* (non-consumables) → leave **Off** — every non-consumable grants its crystals again when restored on another device (`grantProduct` in `src/economy/wallet.ts`), so sharing would hand them to every family member; *Tax Category* → default. The status becomes **Ready to Submit** once step 1 is Active. Do **not** create `weekend_pack` (Phase C, `STORE_LISTING.md` §6.1).

5. **Products, entitlements, offering (one-time, MZ13).** RevenueCat → **Product catalog**: (a) **Products** → **+ New** → app *Tower Clash (iOS)* → *Identifier* = the Product ID → Add, nine times (or **Import**, if offered, and tick the nine). (b) **Entitlements** → **+ New** → identifier → Add → **Attach** the products:

What the code checks (`src/economy/providers/revenueCat.ts`): it **never reads entitlement names** — "Restore Purchases" returns the product id behind each *active* entitlement — so the rule that matters is "every non-consumable is attached to at least one entitlement, no crystal pack is". The three names are those of `docs/MOBILE.md` §8.2 and `ACCOUNTS.md` §5.3; keep them so the dashboard matches the docs. (c) **Offerings** → **+ New** → *Identifier* `default`, *Description* `All products` → Add → in it **Packages** → **+ New** → *Identifier*: custom = the Product ID (e.g. `crystals_100`) → attach the App Store product with the same id → Save, nine packages → mark `default` as the **default (current)** offering. The code reads **all** offerings and keys every package by its product id (`getOfferings().all`), so no offering or package name is required by the code; a product missing from every offering is still fetched by id, but keep all nine in `default`.

6. **The key into GitHub (one-time).** RevenueCat → *Project settings* → **API keys** → the **public** app-specific key of *Tower Clash (iOS)*, starting with `appl_` → Copy → GitHub → *Settings* → *Secrets and variables* → *Actions* → **New repository secret** → name `RC_IOS_KEY` → paste → Add. (Never the secret key `sk_…` — it stays in RevenueCat.) Write "RevenueCat iOS key added" in the report thread.
7. **Build 1.0.1 (team, then you; per version).** The team sets **1.0.1 / build 9** (`package.json` + `npm run version:sync`), writes the 1.0.1 section of `RELEASE_NOTES.md` and names the commit in the daily report. Build numbers are fixed (Producer, 2026-10-03): **7** = the release candidate with Google test ads (TestFlight only), **8** = 1.0.0 with the real AdMob ids (the App Review build, §0c step 9), **9** = 1.0.1 with in-app purchases. You: §0b step 6 (lane **testflight**) → **1.0.1 (9)** appears in TestFlight; the run log shows `VITE_RC_IOS_KEY: set`.
8. **Sandbox test on the iPhone (MZ14, iOS half; per version that changes the shop).** Purchases in a TestFlight build go through Apple's **sandbox**: nothing is charged. On 1.0.1 (9): (a) Shop → Crystals → *Handful of crystals* → buy → +100 crystals. (b) Bundles → *Starter Pack* (listed only after level 5 — finish level 5 first; ECONOMY §4) → buy → +400 crystals, +400 gold, Bronze helmet in Skins. (c) *Remove Ads* → buy → +50 crystals; play past level 6: no interstitial between levels; *Premium Upgrade* now shows instead of *Premium Bundle* → buy → +550 crystals, Gold roof, Royal helmet. (d) Delete the app → reinstall from TestFlight → Shop → **Restore Purchases** → Starter Pack, Remove Ads and Premium Upgrade come back as owned (no interstitials; Bronze helmet, Gold roof and Royal helmet in Skins) and their crystals / gold are credited once, because the fresh install has no record of them; tap **Restore Purchases** a second time → nothing more is added (currency once per purchase, ECON-12). (e) Settings → About → **Support ID** (`$RCAnonymousID:…`) → RevenueCat → **Customers** → *Sandbox data* on → search that id → the purchases are listed. (f) *Premium Bundle* is hidden once Remove Ads is owned, so it needs a second Apple ID: App Store Connect → Users and Access → **Sandbox** → *Test Accounts* → "+" → a name, a new e-mail address that has never been an Apple ID (an alias of your own mailbox works), password, country → Create; on the iPhone Settings → App Store → *Sandbox Account* (bottom) → sign in → buy Premium Bundle → no interstitials, +600 crystals, Gold roof, Royal helmet. If the TestFlight purchase sheet still shows your own Apple ID, use a second internal tester (another person's Apple ID, sheet §7) instead. To repeat a sandbox test: Sandbox → the tester → **Clear Purchase History**. Refunds cannot be tested on Apple from TestFlight; the Android half of MZ14 covers them (Play Console → Order management). Write the results in the report thread (T9).
9. **Submit 1.0.1 (per version).** §0b steps 7–8 with these differences: App Store tab → "+" next to iOS App → version `1.0.1`; *What's New* = the EN block of `RELEASE_NOTES.md` v1.0.1; *Promotional Text* and *Description* = **variant A** (sheet §6.2, `STORE_LISTING.md` §1.1); section **In-App Purchases and Subscriptions** → *Select* → tick all nine → Done (the first products must be submitted with a version); *Build* → **1.0.1 (9)**; *App Review Information → Notes* = **variant A** (sheet §6.4, 878 chars); **App Privacy** → Edit → Purchases → **Purchase History: Yes** (App Functionality, not linked, not tracking — sheet §4 variant A) → Publish; Age Rating → In-App Purchases **Yes** (sheet §5). Then **Add for Review** → **Submit to App Review**; release manually (§0b step 8). Apple reviews the non-consumables against 3.1.1 / 3.1.2 — a failing Restore Purchases is a rejection, hence step 8 first.
